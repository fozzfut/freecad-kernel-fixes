# Ускорение сеток и выбора во FreeCAD 1.1.1: патч BRepMesh и собственная сборка модуля Part

Дата: 21.09.2026. Статус: дизайн одобрен владельцем (разделы 1 и 2), ждёт плана реализации.

## 1. Цель и решения владельца

Владелец остаётся на FreeCAD (замены Coin внутри FreeCAD нет) и хочет все найденные ускорения работы с
сетками и BVH: «любой выигрыш в производительности — в плюс». Источник цифр — исследование
`C:/dev/cad-perf-research` (21.09.2026); независимая проверка там была остановлена, поэтому **каждая
цифра этого документа перемеряется в начале соответствующего этапа**, и приёмка идёт только по новым
замерам.

Решения владельца (21.09.2026):
- C++-патчи FreeCAD ставятся **локально и в портативную сборку HybridDesign**; в upstream не отправляем.
- Сборка FreeCAD — **вариант A** (воспроизвести окружение релиза), «делать до победного», без отката
  на облегчённую сборку против установленных DLL.
- Задачи на стороне HybridDesign (BVH для привязок и измерений, сеточные булевы для превью) переданы
  сессии, которая ведёт переделку HD: `C:/dev/cad-perf-research/HANDOVER-HD.md`.
- Крупные изменения ядра (раздел 10) — отдельными спеками после разделов 3–8.

## 3. Патч BRepMesh (дефект 012)

**Суть** (прототип: `C:/dev/cad-perf-research/tessellation/tkmesh_instr/src` + `patch2..5.py`).
На длинной B-сплайновой грани винта ШВП (грань 170, 4×1305 полюсов, 6,4°) 52–57 % времени уходит на
просмотр описанных окружностей в сетке ячеек 5×5, заданной один раз по граничным узлам и не растущей
до 390 647 треугольников; 35–39 % — на классификацию каждого узла перебором всех 14 149 отрезков
границы. Исправление:
- классификатор узлов по корзинам отрезков — те же ответы, без полного перебора;
- сетка описанных окружностей растёт вместе с числом треугольников; «большие» окружности — отдельным
  списком.

**Приёмка:**
- триангуляции **побитно идентичны** стоковым (узлы, UV, треугольники, полигоны на рёбрах) на 58 телах
  VR6, деталях владельца и ≥60 формах `C:/dev/occt-dataset`, при (0,5 %, 28,5°) и (0,5 %, 6,4°);
- грань 170 ускоряется ≥ 8× (прототип: 134,6–218,8 → 11,0–17,9 с);
- ни одна форма не медленнее стока более чем на 5 % (медиана трёх прогонов, A-B-A в одном процессе);
- пиковая память ≤ сток + 10 % (первый наивный вариант прототипа съел >2,5 ГБ — это причина критерия);
- внутри FreeCAD: открытие VR6 при 6,4° быстрее стока (A/B), headless и GUI-наборы HD зелёные.

**Установка:** как у дефекта 009 — переименование стокового DLL в `.stock-<md5>.bak`, копия патченого,
проверка md5, скрипт отката; права администратора подтверждает владелец (UAC).

## 4. Сборка модуля Part (спайк, подпроект 2)

**Факты.** Релиз 1.1.1 (`0108fd4b4850cc46e625b60e53cea7a7bbe69f8d`, 14.04.2026) собран rattler-build из
рецепта `package/rattler-build`; версии всех зависимостей conda-forge закреплены в `pixi.lock` того же
коммита (`qt6-main 6.8`, `occt 7.8`, `python 3.11`, `coin3d`, `pivy`, `boost`, `tbb 2022`, …).

**Как.**
1. Окружение из `pixi.lock` коммита `0108fd4` для win-64, только с пакетами, нужными модулю Part и его
   зависимостям (App, Base, Gui); версии — ровно из lock-файла.
2. Конфигурация CMake — флаги рецепта rattler-build (важно для ABI: определения препроцессора,
   `FREECAD_USE_*`, режим сборки); лишние модули выключены.
3. Собрать **без изменений**, подменить `Part.pyd` и `PartGui.pyd` в **тестовой копии** FreeCAD
   (не в Program Files).
4. Критерий «неотличима от релиза»: тесты `TestPartApp` и `TestPartGui` самого FreeCAD, headless-набор
   HD (1305 тестов на момент 15.09) и GUI-наборы HD — те же результаты, что на стоке; открытие VR6,
   O-ring и синтетики — те же формы (объём, число граней) и те же массивы Coin.
5. Только после этого — патчи разделов 5–8.

**Диск:** после уборки 21.09 свободно 44 ГБ; окружение + дерево сборки оцениваются в 12–15 ГБ. После
приёмки дерево сборки сжимается до того, что нужно для пересборки Part.

## 5. Перемешивание только изменённых граней (дефект 013)

**Сейчас:** `ViewProviderPartExt` перед мешингом делает `BRepTools::Clean` всей формы
(`ViewProviderExt.cpp:1105–1110` @1.1.1), поэтому каждая правка перемешивает все грани, хотя после
локального выреза 170 из 174 граней — те же `TShape`.

**Дизайн:** реестр в `PartGui` «грань (`TShape`) → (линейный допуск, угловой допуск, указатель на
`Poly_Triangulation`)» для триангуляций, созданных этим мешером. Перед мешингом каждая грань:
реестр совпал по всем трём полям — триангуляция остаётся; иначе очищается **только эта грань**.
Смена `AngularDeflection` (в том числе переход HybridDesign «грубо при правке → точно в простое»,
`gui/edit_mesh.py`) даёт несовпадение — грань перемешивается, поведение HD сохраняется.
Устройство реестра: ключ — адрес `TopoDS_TShape` (сама грань реестром не удерживается), значение —
параметры и `Handle(Poly_Triangulation)`. Совпадение засчитывается, только если у грани **сейчас** ровно
эта триангуляция (сравнение указателей): новая грань, случайно получившая тот же адрес, триангуляции
из реестра не имеет и потому очищается. Записи, чья триангуляция больше никому не нужна (счётчик
ссылок = 1, держит только реестр), удаляются при каждом проходе мешинга.

**Риск, который надо закрыть замером первым:** исследование дало два разных результата.
Тема триангуляции: без `Clean` 2,317 → 0,088 с (26×) и 20,38 → 0,624 с (33×), когда изменились 4 грани
из 174. Тема булевых: 0,5–2× на плитах, где новые грани большие, потому что `BRepMesh_IncrementalMesh`
сам проверяет согласованность всей формы за O(n). Поэтому этап начинается с профиля этой проверки;
если она доминирует, патч включает и её (проверять только грани без годной триангуляции и их рёбра).

**Приёмка:**
- неизменённые грани получают ту же триангуляцию, что при полном перемешивании стоком (сравнение по
  граням; допускается только расхождение, которое сам сток даёт между двумя прогонами — измерено
  8 треугольников на миллион из-за `InParallel`);
- без щелей на стыке старых и новых граней (общие рёбра дискретизированы согласованно; проверка
  свободных рёбер сетки);
- ускорение повторного мешинга на наборе случаев «локальная правка» (O-ring, VR6-деталь, hicmos,
  плиты) — таблица по случаям; цель ≥ 10× там, где изменённые грани малы; нигде не медленнее стока;
- GUI-наборы HD (`edit_mesh`, `progressive`, `through_mesh`, `render_cache`) зелёные.

## 6. `ControlSurfaceDeflection` для сетки отображения (дефект 014)

Параметр `Mod/Part/MeshControlSurfaceDeflection` (bool) читается в `setupCoinGeometry` и передаётся в
`IMeshTools_Parameters`. Замер прошлого исследования: VR6 при 6,4° 59,1 → 8,3 с, ошибка хорды ШВП
0,125 → 0,380 мм при допуске 0,635 мм.

**Значение по умолчанию выбирается замером:** выключено, только если на всех формах набора
(VR6, детали владельца, `occt-dataset`) максимальная ошибка хорды ≤ линейного допуска вида; иначе
по умолчанию включено, а выключение — настройка для больших сборок.

## 7. Сетка отображения в файле (дефект 015)

Для деталей тяжелее порога (порог — по замеру «мешинг против чтения»: прошлый замер 283 мс против 23 мс
на 19 396 треугольниках, мелкие детали дешевле перемешать) сетка сохраняется в FCStd вместе с
параметрами и хешем формы. При открытии: хеш и параметры совпали — узлы заполняются из файла без
мешинга; иначе — обычный мешинг. Сохраняются только сетки, чьи параметры совпадают с текущими
свойствами вида (грубая сетка правки в файл не попадает).

**Формат выбирается в первом шаге этапа по одному жёсткому критерию:** стоковый FreeCAD 1.1.1
открывает такой файл **без ошибок и предупреждений** и получает ту же модель. Кандидаты: треугольники в
BREP формы (стоковый прочтёт и перемешает) плюс отметка параметров; отдельная запись в архиве FCStd,
которую сток игнорирует.

**Приёмка:** VR6 при 6,4° открывается ≤ 3 с (сейчас 48–55 с); рост файла — в таблице по файлам;
стоковый 1.1.1 открывает файл без сообщений в консоли; после правки детали её сетка из файла не
используется (хеш не совпал).

## 8. BVH для выбора мышью (дефект 016)

Сначала профиль: на 1000/5000 деталях предвыбор стоит 2–2,6 / 7,6–12,4 мс (`SoRayPickAction` по
сцене на каждое движение мыши). Определить, что доминирует: проверки треугольников внутри
`SoBrepFaceSet`/`SoBrepEdgeSet` или обход тысяч узлов сцены.
- Треугольники → BVH внутри `SoBrepFaceSet::rayPick` / `SoBrepEdgeSet` (строится лениво при первом
  выборе, сбрасывается при смене сетки).
- Обход → пространственный индекс деталей для предвыбора (`Gui/Selection`, `SoFCUnifiedSelection`),
  тогда поставка включает и `FreeCADGui.dll` — решение фиксируется в плане после профиля.

**Приёмка:** на 10 000 случайных лучей (VR6 + синтетика 1000/5000) результат совпадает со стоком —
та же деталь, тот же элемент (`FaceN`/`EdgeN`/`VertexN`), точка в пределах 1e-6 мм; предвыбор на 5000
деталях ≥ 5× быстрее; подсветка и выделение в GUI-наборах HD без изменений.

## 9. Общие правила для всех этапов

- Замер «до/после» на файлах владельца (копии) и синтетике, A-B-A в одном процессе, машина шумная —
  диапазоны и фоновая нагрузка в отчёте; FreeCAD запускается только через `C:/dev/tools/fcslot.sh`
  (не больше 5 процессов на машине).
- Корректность раньше скорости: для сеток — идентичность или явно измеренное расхождение; для выбора —
  совпадение результатов; для файла — открытие стоком.
- Установка в Program Files — с резервной копией, проверкой md5 и скриптом отката; UAC подтверждает
  владелец. Портативная сборка — через `C:/dev/tools/build-package.ps1`, с исходниками изменений
  (LGPL-2.1: изменённые файлы OCCT и FreeCAD публикуются в этом репозитории).
- HybridDesign обязан работать и на стоковом FreeCAD — патчи ничего не требуют от HD.

## 10. Не входит (отдельные спеки позже)

BVH-классификатор внутри булевых (запрос в 700–1100× быстрее, но классификация — около 23 % булевой
на деталях владельца), настоящее локальное смещение грани (прототип 1,6–2,4 мс против 28 мс…41 с),

(разрез ШВП), тензорная сетка по узловым интервалам. У каждого — корпус корректности (объём, `check`,
симметрическая разность, ~1000 случаев) до установки.
