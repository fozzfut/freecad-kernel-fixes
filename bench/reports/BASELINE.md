# База: стоковый FreeCAD 1.1.1 (+ HybridDesign), 22.09.2026

Это «было» для цели владельца «FreeCAD + мой верстак в 10 раз быстрее, чем сейчас». Все следующие этапы (патчи
012–019, своя сборка Part) сравниваются с этими числами. Серия — `bench/run_matrix.sh stock "C:/Program Files/FreeCAD 1.1" 3`
(так он вызывался до id серий в тегах, коммит `cafc174`), журнал — `bench/runs/matrix-stock.log`, каждое число ниже — медиана
по прогонам `bench/runs/stock-<файл>-<профиль>-r<k>/result.json`, таблицы собраны `python tools/baseline.py runs stock`.
Для `report.py` и `tools/baseline.py` эта серия называется `baseline` (её теги без префикса серии; прогоны не
переименовывались, и новые серии этого имени не получают).

**Что измерено.** Установленный FreeCAD (`C:/Program Files/FreeCAD 1.1`, `1.1.1 20260414 (Git shallow)`), оффскрин,
кадр 1920×1080, настройки владельца (копия его `user.cfg`, у деталей 6,4°). Профиль `fc` — чистый FreeCAD, `hd` —
плюс HybridDesign (коммит `19825927af741ce9a69d875f98c69d7c9c44f065`, как записали прогоны). Три повтора на каждую пару
«файл × профиль»; зачётен только прогон с пустым `errors` в `result.json`.

## Что это значит для владельца

**Без HybridDesign (профиль fc — по нему судятся исправления ядра).** Самое долгое — **открыть тяжёлый файл**.
Нынешний VR6 открывается ~55 с (медиана `open.open_s` 54,7 с, разброс 50,3–71,1), прежняя копия — 63 с. Почти всё это
время — внутри `openDocument`: первый кадр после него — 0,11 с, занятый цикл событий — 0,16 с. Что внутри
`openDocument` это построение сеток отображения при 6,4°, а не чтение файла, видно по HD на том же файле: откладывая
точную сетку, он открывает его за 5,4 с. На модели из 1000 деталей открытие — 191 с и 2,0 ГБ памяти; самые тяжёлые
детали там — 8 резьб по 654 604 треугольника при 6,4° (`hover.heavy_triangles`), по деталям время открытия этот замер
не раскладывает.

Второе — **правка STEP-детали** (Part::Cut на теле из 450 граней): 2,3 с на правку (VR6 прежний — 2,8 с), из них 2,1 с
(2,6 с) — сам пересчёт, то есть булева операция ядра; кадр после неё — 0,14 с.

**Вращение, наведение и выделение** на VR6 — 80–100 мс на кадр или отклик (облёт всей модели ≈ 10–13 кадров в
секунду): заметно «вязко», но терпимо. На 1000 деталях — 0,37 с на кадр облёта, 0,65 с на отклик наведения и
выделения: работать почти нельзя. **Сохранение** — 1,8–2,2 с на VR6.

Маленькая деталь (O-ring) быстрая: правка `Pad.Length` — 0,17 с, из них пересчёт 0,04 с, остальное — занятый цикл
событий после пересчёта (0,13 с).

**С HybridDesign (профиль hd — что владелец чувствует).** VR6 открывается за 5,4 с (`open_s`; первая грубая картинка по
отметке HD — через 3,2–5,8 с), но до качества из файла (6,4°) HD доводит сетку ещё ~80 с во втором процессе
(`hd_refine_s` 79,7 с; своя отметка HD `full_quality_s` 55,2–81,2 с, `runs/stock-vr6cur-hd-r1..3`; у прежней копии vr6 —
54,6–86,8 с). Правка STEP-детали до первой картинки — 2,0 с, и
ещё ~5 с доводки (`edit_cut.hd_refine_after.wait_s`). Облёт, наведение и выделение на VR6 — те же 75–95 мс. На 1000
деталях HD не выигрывает: `open_s` 25 с, но цикл событий занят ещё ~170 с (медиана `idle_s`), первая картинка по отметке HD — через
19–38 с, полное качество — через 195 с (у FreeCAD 191 с); облёт 0,23 с на кадр, наведение 0,40 с, выделение 0,57 с.
O-ring с HD — 0,31 с на правку (цикл событий занят 0,25 с против 0,13 с без HD).

**Не измерено в этой серии.** `s5000` и плита с 1024 отверстиями (`holes`) требуют 8 ГБ свободной памяти (открытие
плиты — до 7,1 ГБ рабочего набора). Свободной памяти за день было 2,8–5,4 ГБ (VS Code один занимал 3,4 ГБ, остальное —
сессии других прогонов): первое окно ожидания (60 мин, 13:38–14:41) ничего не дало, и по правилу все 12 прогонов
записаны `SKIP-lowmem`; второе окно (14:41–15:33) остановлено решением контролёра — владелец попросил закончить задачу на
имеющихся прогонах. Для этих двух файлов в базе — ни одного зачётного повтора. **Правило владельца от 22.09: не больше
2 ГБ на тестовый процесс** — поэтому `s5000` и `holes` линейкой не гоняются вообще («не измерено: бюджет памяти»).
Плита оценивается по одной грани (зонд 012, `C:/dev/fckf-012-probe/holes`), большие сборки — только в итоговой
интеграции и только если машина свободна. Пики зачётных прогонов: O-ring 0,6 ГБ, VR6 1,2 ГБ, s1000 без HD 2,0 ГБ
(на пределе).
Прежние прогоны на том же файле плиты и
том же FreeCAD (вне серии, только `fc`): открытие 95,1 с, правка скругления — медиана 107,6 с при загрузке 78 %
(`runs/t3-holes-r1/result.json`); одна правка 79,9 с при 63,5 % (`runs/t3-holes-odd/result.json`). По ним правка
скругления на плите — самое медленное действие из всех (~1,5 минуты на одно изменение радиуса).

## Отступления от плана (и почему)

- **Синтетические файлы показаны.** `synthetic_*_copies.FCStd` записаны FreeCADCmd — в них нет `GuiDocument.xml`, и в
  GUI все детали открывались скрытыми: `runs/t4-s1000-hidden` (исходный файл) — 0 попаданий наведения из 144,
  0 целей выделения, кадр облёта 9 мс (пустая сцена). Серия идёт по копиям с показанными деталями:
  `synthetic_1000_copies_vis.FCStd` сохранён самим FreeCAD (`tools/make_visible.sh`), для 5000 деталей это не удалось
  (показ 5000 деталей по одной не закончился за 580 с, дважды, `runs/make-visible-synthetic_5000_copies_vis/progress.log`
  — само по себе находка для плана ускорения), поэтому `synthetic_5000_copies_vis.FCStd` собран
  `tools/add_gui_visibility.py` (минимальный `GuiDocument.xml` с `Visibility=true`). Что это одна и та же сцена,
  проверено на 1000 деталях: открытие 156,9 с против 152,6 с, облёт 342 против 334 мс, те же 21 попадание наведения
  (`runs/t4-s1000vis-probe`, `runs/t4-s1000xml-probe`). md5 обоих — в `files/MD5SUMS.txt`. Детали получают
  тесселяцию по умолчанию из настроек владельца — 6,4°.
- **s5000 требовала бы 8 ГБ**, как плита (по правилу 2 ГБ не гоняется): видимая s1000 доходит до 2,0 ГБ рабочего набора, s5000 — впятеро больше деталей.
- **Плита — 2 правки скругления на прогон** (`BENCH_FILLET_REPS=2`), не 4: 4 правки заняли 540 с из 600 при 78 %
  загрузки (`runs/t3-holes-r1`), потолок одного запуска — 600 с.
- **Порядок.** Сначала один полный проход, затем повторы 2–3; прогоны, которым нужны 8 ГБ, — в конце, чтобы ожидание
  памяти не держало остальные (`SET=small` / `SET=big` в `run_matrix.sh`). После первого `SKIP-lowmem` остальные
  8-гигабайтные прогоны того же вызова записываются `SKIP-lowmem` сразу (с итогового ревью ожидание памяти — не
  больше 10 мин, одна попытка).
- **Свод.** Таблицы ниже строит `tools/baseline.py` только по зачётным прогонам серии (`stock-<метка>-<профиль>-r<k>`),
  с теми же метриками, что и `report.METRICS`, плюс разбивка правок (пересчёт / цикл событий / кадр) и доводка HD.
  До итогового ревью `report.py runs stock stock` брал все прогоны варианта `stock` в `runs/`, включая отладочные
  (`smoke-*`, `fix*-*`, `t3-*`); теперь он берёт только зачётные прогоны одной серии:
  `python report.py runs baseline <база> <вариант>` для этой серии, `python report.py runs <серия> <база> <вариант>` для
  новых.

## Странности в числах (объяснены)

- **s1000 открывается 149–195 с, а «s5000» в первой попытке — за секунды.** Первая попытка серии шла по исходным
  `synthetic_*_copies.FCStd`, в которых все детали скрыты (нет `GuiDocument.xml`): скрытая деталь не получает сетку
  отображения, открытие — только чтение файла. Замеры на исходных файлах: 1000 деталей — `open_s` 4,1 с, пик 0,72 ГБ;
  5000 — 9,3 с, пик 1,5 ГБ; облёт 8 и 28 мс на кадр, 0 попаданий наведения, 0 целей выделения
  (`runs/t4-s1000-hidden/result.json`, `runs/t4-s5000-hidden/result.json`). Прогоны первой попытки заменены прогонами по
  `*_vis`-копиям; число 149 с — `open_s` зачётного `stock-s1000-fc-r1` уже по показанной модели (медиана трёх — 191 с).
  По показанной s5000 зачётных прогонов нет (см. «Не измерено»).
- **Ошибка `hover_heavy` у s5000 (и у s1000 первой попытки).** Это та же скрытая сцена: сетка наведения 16×9 не задела
  ни одной детали — «тяжёлой детали» нет, и прогон честно помечен ошибкой, а не записан пустой метрикой. На показанных
  копиях сетка попадает (s1000 — 21 точка из 144, 21 деталь).
- **`hover.heavy` в базе держится на 1–2 точках.** Тяжёлую деталь сетка 16×9 задевает в 1 точке на s1000 и в 2 на
  VR6 (`hover.heavy.n` в `result.json` каждого прогона), и тогда «медиана» прогона — это одна точка или, по правилу
  медианы того времени (`s[n//2]`), более медленная из двух: поэтому `heavy.median` и `heavy.max` в таблицах совпадают.
  С итогового ревью плана A прогон добирает до 12 точек внутри экранного габарита детали (`heavy_sampling`), а
  `report.py` помечает `heavy` с n < 5; `heavy_grid` — прежнее определение, по одной сетке. Сравнивать новые прогоны
  с этими строками базы напрямую нельзя — только прогоны одной чередующейся серии.
